# Docker

How BikeTR runs locally with Docker Compose: the services, how they reach each other, and what a restart picks up.

## Gotchas

- **An app section named like a service needs its own nginx rule**: app addresses have no `#` (`/coach`, `/analisi`), and nginx sends `/coach` to `/coach/`, the Coach service, because of the `location /coach/` prefix. `location = /coach` in `docker/nginx/default.conf.template` sends the bare address to the app; a new section or service sharing a name needs the same.
- **Mounted config and server code need a recreate**: nginx builds its configuration from `docker/nginx/default.conf.template` and the auth server loads `docker/auth/server.ts` only when their containers start, and `docker compose up -d` does not restart a container when only a mounted file changed. After editing files under `docker/`, or pulling a version that changes them, run `docker compose up -d --force-recreate` (what the README tells users); until then new routes answer 404. The Coach service runs uvicorn without `--reload` on its mounted `docker/coach` code, so after changing `docker/coach/app` run `docker compose restart coach`; until then a new route answers 405 or 404. A restart also loads the image as it is: if the Coach then exits with `ModuleNotFoundError`, the image is older than `requirements.txt` (next entry), and `docker compose up -d --build coach` fixes it.
- **A changed `requirements.txt` needs a rebuild**: Compose builds the `coach` image only when it is missing, so after pulling a version that adds a Python package the old image stays and the tests fail at import (`ModuleNotFoundError: No module named 'sqlite_vec'` after passage-search). Run `docker compose build coach` (or `up -d --build`) after a pull that touches `docker/coach/requirements.txt` or its Dockerfile.
- **Docker's DNS ignores `extra_hosts`**: nginx resolves upstreams through Docker's DNS (`resolver 127.0.0.11`), which does not read the container's `/etc/hosts`, so an `extra_hosts` entry has no effect on `proxy_pass` targets. `host.docker.internal` resolves only because Docker Desktop's own DNS knows it; the host-Ollama option therefore needs Docker Desktop and fails on a plain Linux Docker Engine.
- **A missing single-file bind mount becomes a folder**: mounting `./some-file.json` into a container when the file does not exist makes Docker create an empty folder with that name in the project, and `git restore` of the file then fails. To give a service one project file, let it fetch the file from nginx (`http://web/<file>` with header `Host: localhost`, since nginx refuses other host names), as the Coach service does for `papers_index.json`.
- **nginx closes an idle live-reload connection after 60 seconds**: the WebSocket between the page and Vite stays silent when nothing changes, and nginx's default `proxy_read_timeout` (60 s) drops it; Vite's client then waits for the server and reloads the page, losing unsaved form input. The `location /` proxying to the `app` service keeps `proxy_read_timeout 1d`.
- **nginx redirects drop the browser's port**: inside the container nginx listens on 80, so `return 302 /path` sends `Location: http://localhost/path` and the browser leaves port 5050. Add `absolute_redirect off;` to the location, which sends the path alone (as the `/activity.html` redirect does).
- **The Phoenix image starts as root**: its Dockerfile names a non-root user, but the published image runs as user 0. `compose.yaml` runs it as `65532:65532` with the `phoenix-data` volume on `/home/nonroot`, the folder that user owns. A volume mounted on a path the image lacks is created owned by root, and Phoenix can't write its database.
- **Don't block dot-paths in front of Vite**: Vite serves pre-bundled packages under `/node_modules/.vite/deps/`, so a "deny hidden files" rule such as `location ~ /\.` breaks the app. Hidden project files stay safe because the `app` container mounts only `web/` and nginx serves nothing else from the project folder except `/papers_index.json`.
